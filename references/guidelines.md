# GEB分形文档系统指南

## 系统概述

GEB（Gödel, Escher, Bach）分形文档系统是一种保持代码与文档同构的文档规范。**核心教义**：代码是机器相，文档是语义相，两相必须同构。任一相变化必须在另一相显现。

### 三层分形结构

| 层级 | 位置 | 职责 | 触发更新 |
|------|------|------|----------|
| L1 | `/CLAUDE.md` | 项目宪法·全局地图·技术栈 | 架构变更/顶级模块增删 |
| L2 | `/{module}/CLAUDE.md` | 局部地图·成员清单·暴露接口 | 文件增删/重命名/接口变更 |
| L3 | 文件头部注释 | INPUT/OUTPUT/POS 契约 | 依赖变更/导出变更/职责变更 |

### 契约关系

```
代码变更
    ↓
L3 检查 → INPUT/OUTPUT/POS 与实际一致?
    ↓
L2 检查 → 文件增删? 职责变? 接口变?
    ↓
L1 检查 → 模块增删? 技术栈变?
    ↓
文档更新
```

### 成员清单规范

每个成员条目包含：
- **文件名**：必须包含扩展名
- **职责**：一句话说明做什么
- **技术细节**：使用的关键技术或方法
- **关键参数**：重要的配置或参数（可选）

示例：
```markdown
index.html: 主页面实现，包含样式、脚本和交互逻辑
utils.js: 工具函数集合，提供日期处理、数据验证等功能
```

## L3 文件头部契约模板

```javascript
/**
 * [INPUT]: {依赖的具体能力来源}
 * [OUTPUT]: {对外提供的具体内容}
 * [POS]: {所属模块} 的 {角色定位}，{与兄弟文件的关系说明}
 * [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md
 */
```

### 契约要素详解

#### INPUT（输入）
说明文件依赖的外部资源：
- 其他模块的导出
- 全局变量
- 外部API
- 配置文件

示例：
```javascript
/**
 * [INPUT]: 依赖 i18n.js 的语言切换能力，依赖 ticket.js 的电影票渲染逻辑
 * [OUTPUT]: 提供电影票风格主页的完整渲染功能
 * [POS]: src/ 模块的主页面组件，整合其他功能模块
 * [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md
 */
```

#### OUTPUT（输出）
说明文件对外提供的内容：
- 导出的函数/类
- 暴露的变量
- 生成的文档
- 提供的服务

#### POS（定位）
说明文件在系统中的位置和关系：
- 所属模块
- 角色定位
- 与其他文件的关系

#### PROTOCOL（协议）
变更时需要执行的步骤：
1. 更新本头部
2. 检查上级CLAUDE.md

## 正向工作流（代码→文档）

### 步骤1：修改代码
- 完成代码实现或修改
- 确保功能正确

### 步骤2：L3检查
- 检查文件头部注释
- 确保INPUT/OUTPUT/POS与实际一致
- 如有不符，更新头部

### 步骤3：L2检查
- 检查模块CLAUDE.md
- 文件是否有增删？
- 职责是否变更？
- 接口是否变更？
- 如有变更，更新成员清单

### 步骤4：L1检查
- 检查项目CLAUDE.md
- 模块是否有增删？
- 技术栈是否变更？
- 如有变更，更新项目宪法

### 步骤5：完成
- 文档与代码保持同步
- 系统状态清晰

## 逆向工作流（进入目录）

### 步骤1：进入目录准备
- 准备进入新目录
- 了解项目结构

### 步骤2：读取L1
- 读取项目CLAUDE.md
- 理解整体架构
- 如果不存在，标记待创建

### 步骤3：读取L2
- 读取目标目录CLAUDE.md
- 理解模块职责
- 如果不存在，创建L2文档

### 步骤4：读取L3
- 读取目标文件头部
- 理解文件契约
- 如果不存在，添加L3头部

### 步骤5：开始工作
- 理解上下文
- 开始实际开发

## 禁止行为

### 死罪（立即中止）
- **FATAL-001**：孤立代码变更
  - 错误：只改代码，不更新文档
  - 正确：代码变更必更新对应文档
  
- **FATAL-002**：跳过L3创建
  - 错误：发现缺失头部继续工作
  - 正确：立即添加L3头部再继续
  
- **FATAL-003**：删文件不更新L2
  - 错误：删除文件后成员清单残留
  - 正确：同步更新成员清单
  
- **FATAL-004**：新模块不创建L2
  - 错误：创建新模块但没有文档
  - 正确：同时创建L2文档

### 重罪（警告后修复）
- **SEVERE-001**：L3过时
  - 头部与代码不符
  - 修复：更新头部匹配代码
  
- **SEVERE-002**：L2不完整
  - 存在未列入清单的文件
  - 修复：更新成员清单
  
- **SEVERE-003**：L1过时
  - 目录结构变化未反映
  - 修复：更新项目宪法
  
- **SEVERE-004**：父级链接断裂
  - L2中的父级路径错误
  - 修复：修正父级引用

## 工具和脚本

### 文档检查脚本
```bash
#!/bin/bash
# check-geb.sh
echo "检查GEB文档系统..."

# 检查L1
if [ ! -f "CLAUDE.md" ]; then
    echo "错误: 缺少项目CLAUDE.md (L1)"
    exit 1
fi

# 检查L2
for dir in */; do
    if [ -d "$dir" ] && [ "$dir" != "node_modules/" ]; then
        if [ ! -f "${dir}CLAUDE.md" ]; then
            echo "警告: 缺少 ${dir}CLAUDE.md (L2)"
        fi
    fi
done

# 检查L3
find . -name "*.js" -o -name "*.html" -o -name "*.css" | while read file; do
    if [[ "$file" != *"node_modules"* ]]; then
        if ! grep -q "\[PROTOCOL\]" "$file"; then
            echo "警告: 缺少L3头部 $file"
        fi
    fi
done

echo "检查完成"
```

### 文档更新脚本
```bash
#!/bin/bash
# update-geb.sh
echo "更新GEB文档系统..."

# 更新L3头部
find . -name "*.js" -o -name "*.html" -o -name "*.css" | while read file; do
    if [[ "$file" != *"node_modules"* ]]; then
        # 检查并更新头部
        echo "检查 $file"
    fi
done

# 更新L2成员清单
for dir in */; do
    if [ -d "$dir" ] && [ "$dir" != "node_modules/" ]; then
        echo "更新 ${dir}CLAUDE.md"
    fi
done

# 更新L1项目宪法
echo "更新 CLAUDE.md"

echo "文档系统更新完成"
```

## 最佳实践

### 文档写作原则
1. **简洁性**：文档要简洁明了
2. **准确性**：与代码保持一致
3. **及时性**：变更同步更新
4. **完整性**：覆盖所有重要信息

### 文档维护建议
1. **每次提交前检查**：确保文档同步
2. **定期审查**：每月检查一次文档状态
3. **团队培训**：让团队成员了解规范
4. **工具辅助**：使用脚本自动化检查

### 常见问题解答

**Q: 文档太繁琐，影响开发速度？**
A: GEB系统看似繁琐，但长期看能节省大量理解成本。初期投入，长期受益。

**Q: 如何平衡文档和开发？**
A: 将文档更新作为开发步骤的一部分，像写测试一样自然。

**Q: 项目小也需要GEB吗？**
A: 正是因为项目小，更需要清晰的文档。大项目有团队，小项目只有你。

**Q: 文档可以自动化生成吗？**
A: 部分可以，但契约关系需要人工维护。自动化只能辅助，不能替代。

## 总结

GEB分形文档系统的核心价值：
- **保持同步**：代码与文档同构
- **清晰边界**：明确职责和接口
- **减少混乱**：避免文档黑洞
- **提高效率**：长期节省理解成本

记住：架构即认知，文档即记忆，变更即进化。
